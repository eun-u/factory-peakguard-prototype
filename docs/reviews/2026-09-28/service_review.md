## 1. 이번 중간 정리의 판단

**현재 서비스는 제조 전력의 피크 위험을 연구하고 운영자가 판단을 검토하는 시제품이다. 도메인 고도화의 다음 목표는 예측값을 현장 상태·실행 제약·조치 결과와 연결하는 것이다.**

시간순 평가, 미래 정보 차단, 기준선 비교, 불확실성 평가, 사전 채택 기준, 재현 기록은 이미 중요한 기반이다. 반면 현재 저장소만으로는 실시간 공장 연동, 설비별 실행 가능성, 실제 절감 효과, 현장 조치의 성공을 입증할 수 없다. 모델 연구의 완료와 현장 서비스의 완성을 구분해야 한다.

이번 문서는 서비스 코드, 최신 선정 기록, 기존 보고서, 운영 시나리오, 제출·동결 경계를 검토했다. `C:\Project\피지컬AI시스템설계`의 참고서 지식을 설계 관점으로 적용했다. **서비스 코드·모델·평가 기준을 바꾸는 작업은 수행하지 않았으며, 아래 수정 항목은 후속 작업안이다.** 새 자료는 기존 보고서를 대체하는 최종 제출물이 아니라 최신 상태를 보완하는 내부 중간 정리다.

우선순위는 다음과 같다.

1. **P0 — 현재 결과의 의미와 출처 정합성:** 시연 앱·연구 결과·최종 평가 상태를 분리하고, 단위·시간 구간·모델·선정 근거를 일관되게 표시한다.
2. **P1 — 현장 판단에 필요한 도메인 계약:** 계량기·설비·공정·작업·제약의 관계, 예보의 유효시점, 조치 가능성, 운영자 결과 기록을 정의한다.
3. **P2 — 검증된 확장:** 현장 관측 연동과 그림자 운영, 조치 반응 검증, 제한적 실증을 거쳐 운영 효과를 평가한다.

P0/P1/P2는 이 문서의 **개선 우선순위**다. 과거 연구의 P1·P2·P3 단계와 다른 구분이다.

### 2.1 시연 앱과 연구 엔진의 차이

| 항목 | 과거 시점 시연 앱 | 최신 연구 파이프라인 |
|---|---|---|
| 자료 접근 | `source.zip`의 전체 역사 자료를 로딩 | 개발 목표를 2021-08-09 09:45 이전으로 제한 |
| 화면/평가 시점 | 기본 선택이 역사 자료의 마지막 시점; 선택 시점 이전으로 학습 | 사전 정의한 개발 rolling-origin 3폴드 |
| 예측거리 | 15·30·60분 | 15분·1시간·4시간·24시간 |
| 모델 | HistGradientBoosting, persistence, 전주 동일 시각 | 선정된 persistence/CBL/LightGBM 및 분위수 B |
| 불확실성 | 보정 구간 절대잔차의 90% 분위수를 양쪽에 적용 | q90/q95 등 분위수와 보정의 개발 평가 |

**시연의 시간 누수 방지와 연구의 최종 테스트 봉인은 서로 다른 조건이다.** 시연 앱이 선택 시점 이후를 학습에 쓰지 않더라도, 전체 역사 로더와 마지막 날짜 기본값은 연구의 보류 구간과 겹칠 수 있다. 연구 검토용 화면에서는 개발 구간으로 제한된 별도 입력을 사용해야 한다. 이번 검토에서는 시연 앱을 실제 원자료로 실행하지 않았다.

화면의 예측 범위를 연구 q95나 검증된 초과 확률로 해석해서도 안 된다. 같은 이름의 “피크”와 “불확실성”이라도 산출 절차가 다르므로, 공통 계약을 만든 뒤 모델·보정법·평가 범위를 명시해야 한다.

## 3. 성과와 한계를 함께 읽기

### 3.1 4시간 후보: 오경보 감소와 피크 오차 악화

동일 개발 평가에서 기존 CBL과 채택 잔차 모델을 비교한 결과다. 전력 단위는 미확인이며, 위치 FP는 점예측의 임계값 초과 평가다.

| 지표 | 기존 CBL | 채택 잔차 모델 | 판단 |
|---|---:|---:|---|
| 피크 위치 MAE | 15.285 | 19.778 | 악화; 평균 피크 오차 개선 미입증 |
| 위치 오경보 FP | 978 | 493 | 감소; 사전 선정 순서의 후순위 CI 근거 |
| 에피소드 F1 | 0.496 | 0.511 | CI가 겹침; 우월성 단정 불가 |
| 첫 폴드 피크 MAE | 23.760 | 68.570 | 조건별 취약성을 보여주는 큰 악화 |

피크 MAE 개선량은 **기존−후보 = −4.492, 95% CI [−12.073, 0.407]**다. 반올림된 두 표시값의 차이는 원 수치 차이와 끝자리가 다를 수 있다. 마지막 폴드 10% 악화 배제 기준은 통과했지만, 모든 폴드 안정성을 검증한 것은 아니다. 기존 채택 판단은 보존하고, 다음 개발 주기에는 초반 폴드·조건별 악화를 다루는 기준을 결과 전에 별도로 정할 수 있다.

**이 FP 감소는 실제 운영 경보 감소나 현장 조치율 향상과 동일하지 않다.** q95 위험 모델 B는 그대로여서, 준비 30/60분·D20% 시나리오의 피크 출발창 조치 가능 수는 172/183으로 동일했다. 이는 사후 관측 생산량·회귀 계수·준비시간 가정에 따른 결과이며, 실제 실행 172건이나 실현 절감률이 아니다. 완벽정보 참고 178/183도 고정 발령 규칙의 비교값이며 전역 최적 상한이 아니다.

전력 서비스에 대한 System 1/2 대응, 계량기 온톨로지, 조치 상태기는 **설계 전이안**이다. 로봇 VLA, 월드모델, 강화학습을 현재 모델에 추가해야 한다는 결론은 나오지 않는다. 통계 모델과 규칙만으로도 필요한 인터페이스와 검증 구조를 먼저 만들 수 있다.

참고 지식은 제공된 **159개 캡처**의 구조화 결과다. QA의 `PASS_WITH_DOCUMENTED_REVIEW`는 캡처 처리·출처 관리에 대한 결과이며 책 전체의 과학적 주장이나 연구 재현을 보증하지 않는다. OCR은 `UNVERIFIED_OCR`; 판권면 캡처 0002 하단은 `REVIEW_REQUIRED`다. 캡처 번호와 인쇄 페이지는 다른 식별자다. 이번 제안은 관련 장·페이지 노트를 사용했고, 책의 세부 성능 수치를 재인용하지 않았다.

| 15분 구간 | HH:15/30/45 및 다음 HH:00에 끝난다는 가정 | 시작·종료 시각, 타임존, 경계 포함 규칙, 수집 지연과 정정 정책 |
| 통계적 피크 | 학습 구간 상위 5% 초과 | `statistical_peak`로 명시; 적용 학습 기간과 임계값 버전 보존 |
| 운영 경계 | 아직 확인되지 않은 현장 기준 | 계약/설비 용량/현장 목표 중 어떤 경계인지, 대상 계량기와 유효기간 확인 |
| 요금 피크 | 계약·단가·실제 청구 조건 미확인 | 통계적 피크와 별도 관리; 공식 계약·단가 확인 후 계산 가능 여부 결정 |
| 재가동·교대 | 시간대·달력·생산량 대리변수 | 실제 설비 모드와 교대·휴식·재가동 사건은 별도 수집; 대리변수를 실측 라벨로 취급하지 않음 |
| 부하 이동 | 생산량 일부를 다른 시각으로 이동하는 가정 | 이동 가능한 작업·제약·준비시간·목적 시간창·실제 실행 여부가 있는 권고 |
| 절감 효과 | 가정 기반 시나리오 차이 | 예측 차이, 시뮬레이션 차이, 관측된 변화, 인과적으로 추정된 효과를 구분 |

단위 확인 전에는 kW/kWh 변환이나 원화 절감 계산을 제시하지 않는다. 비용 목적함수도 실제 계약 정보가 없으면 무차원 민감도 수준으로 남긴다. 전력 저감만을 목표로 삼으면 생산량 감소·납기 지연·반동 피크를 놓칠 수 있으므로 생산·품질·제약 위반을 함께 관찰해야 한다.

### 5.2 최소 도메인 관계

초기 구현은 관계형 테이블과 검증 규칙으로 충분하다. 그래프 DB나 온톨로지 추론 엔진 도입은 실제 검색·변경관리 요구가 생긴 후 판단한다.

| 개체 | 핵심 연결 | 필요한 속성 | 현재 자료로 확정 가능한가 |
|---|---|---|---|
| 공장/계측 범위 | 계량기가 어떤 경계를 측정하는가 | site_id, meter_id, 측정 경계, 유효기간 | 세부 계량기 범위 확인 필요 |
| 논리 설비 / 물리 자산 | 공정 역할을 어떤 실제 장비가 수행하는가 | equipment_id, asset_id, 배치·교체 기간 | 없음; 현장 연계 필요 |
| 공정/작업 | 설비에서 어떤 작업을 수행하는가 | process_id, job_id, 제품/로트, 선후행, 마감 | 없음; MES·계획표 등 필요 |
| 운전 상태 | 시점별 가동·대기·정지·재가동 | event_time, available_at, mode, 출처 | 시간·생산량 대리정보만 있음 |
| 이동 가능 부하 | 어떤 작업을 언제 얼마나 이동 가능한가 | 최소 운전/정지, 준비시간, 이동량, 금지 시간창 | 사후 가정이며 실측 제약 없음 |
| 피크 정책 | 어떤 범위에 어떤 임계값이 유효한가 | 종류, threshold, unit, valid_from/to, 근거 | 통계적 피크 기준만 개발 정의 |
| 예보/권고/조치 | 어느 예보가 어떤 판단·실행으로 이어졌는가 | forecast_id, decision_id, action_id, 버전, 상태 | 개발 예측·분석은 존재; 현장 사건 연결은 제안 |

논리 설비와 물리 자산을 구분하는 관점은 [OPC Foundation ISA-95 Common Object Model §8.2.1](https://reference.opcfoundation.org/ISA-95/v100/docs/8.2.1)을 참고했다. 특정 통신 방식이나 표준 준수 인증을 이미 구현했다는 뜻은 아니다. 계량기–설비의 관계도 단순 1:1로 가정하지 않고 계측 범위와 변경 이력을 먼저 확인한다.

## 6. 목표 서비스 흐름과 데이터 계약 — 제안

### 6.1 권고가 운영 판단으로 이어지는 흐름

1. **관측:** 계측값과 도착 시각을 수집하고 결측·정정·단위·시계 상태를 확인한다.
2. **상태 구성:** 해당 시점에 알려진 생산 계획·설비 상태·제약만 결합한다.
3. **예측:** 점예측·불확실성·대상 시간 구간·모델 버전을 함께 발행한다.
4. **위험 판단:** 통계적 피크와 현장 운영 경계를 구분하고, 경보가 유효한 시간을 정한다.
5. **조치 후보:** 대기, 운영자 점검, 승인된 작업의 지연 등 정의된 후보만 비교한다.
6. **제약 검사·승인:** 작업 선후행·최소 운전시간·준비시간·납기·품질·중복 권고를 확인하고 운영자가 승인 또는 거절한다.
7. **실행·결과 확인:** 실행 주체가 실제 시작/완료와 예외를 기록한다. “승인”과 “실행 완료”는 별도다.
8. **검수·다음 평가:** 실제 부하·생산 결과를 연결하고 실패 사례를 선별한다. 새 모델은 별도 평가와 승인 후 배포한다.

현재 구현은 관측 이력, 예측 연구, 위험 분석, 시나리오 검토에 집중되어 있다. 5~8의 현장 워크플로는 후속 설계다. 개발 시나리오에 조치 행이 있다고 해서 현장 실행 기록이 존재하는 것은 아니다.

### 6.2 최소 메시지 계약

다음은 권장 필드이며 현재 API 사양이 아니다. `available_at`은 이벤트가 발생한 시각과 다를 수 있다. 미래 계획도 발행 시각과 개정 이력을 알아야 원점 기준 재현이 가능하다.

| 메시지 | 필수 필드 제안 | 검증 규칙 |
|---|---|---|
| Observation | meter_id, interval_start/end, event_time, available_at, value, unit, quality, source_id, revision_id | 단위·시간 경계 미확인 상태 보존; 정정 이력 덮어쓰기 방지 |
| PlantState | as_of, equipment/process/job_id, mode, constraints, provenance | 예측 원점에 알려진 상태만 사용; 미확인을 정상 상태로 치환하지 않음 |
| Forecast | forecast_id, origin, target_start/end, issued_at, valid_until, model_version, data_snapshot_id, point, quantiles, calibration_version | 목표 구간과 거리 일치; 점예측·분위수·확률을 구별; 만료 예보로 새 조치를 만들지 않음 |
| Decision | decision_id, forecast_id, policy_version, threshold_type/version, candidate_action, feasibility, reason_codes, evidence_scope | 위험이 높아도 실행 제약 미확인 시 승인 가능한 조치로 승격하지 않음 |
| Action | action_id, decision_id, proposed/approved/started/completed_at, actor_role, status, rejection/abort_reason | 중복 명령 방지; 승인·실행·완료 구별; 유효시간 만료 시 재검토 |
| Outcome | action_id, observation_ids, realized_peak, production/quality_result, exceptions, evaluation_method | 관측 변화와 추정 인과효과를 구분; 조치 없음/거절 사례도 보존 |

증거 유형은 `observed`, `proxy`, `predicted`, `simulated`, `operator_confirmed` 등으로 구분하는 안을 권장한다. 확인 상태·출처·가용 시각을 필드로 유지하여 예측이나 시뮬레이션이 실측 사실로 바뀌지 않게 한다.

### 6.3 두 가지 상태를 분리

현재 네 가지 판정은 위험 검토용 분류다. `NORMAL`은 현재값과 15·30·60분 점예측이 임시 임계값 아래이고 입력 품질·예측구간 폭·기준선 대체에 따른 검토 사유가 없는 상태다. 설비 안전의 보장으로 해석하지 않는다. 기존 판정 로직은 그대로 두고 다음 상태 축을 추가하는 방안을 검토한다.

- **위험 상태:** 정상 관찰 / 피크 주의 / 운영자 확인 필요.
- **조치 상태:** 제안 → 제약 확인 → 승인 또는 거절 → 실행 중 → 완료 또는 중단. 각 단계에서 만료 가능.

예보 데이터가 지연되거나 모델이 실패하면 사전에 정의한 기준선·수동 관찰로 전환하고 전환 이유를 남기는 안이 필요하다. 자동 제어 연동 여부는 별도 제품 결정이며 이번 고도화안의 전제 조건이 아니다. 향후 OT 접속을 검토할 때는 성능·가용성·안전의 제약을 함께 다루는 [NIST SP 800-82 Rev.3](https://csrc.nist.gov/pubs/sp/800/82/r3/final)를 참고하되, 이를 현재 서비스의 인증이나 적합성으로 표현하지 않는다.

R03을 처리하려고 현재 `run_all.py --from report`를 무조건 실행해서는 안 된다. 현 진입점은 기본/개발 외 단계에 날짜·사람 승인 게이트를 적용한다. 문서만 새로 만드는 경로가 필요하면 **holdout을 디코딩하지 않는 개발 전용 보고서 경로를 별도 설계**하고 보호 테스트를 먼저 적용해야 한다. 이번 중간 정리 생성기는 기존 개발 요약·표만 읽는 독립 경로다.

| B. 개발 이력 재생 | 고정 개발 예보를 공통 계약으로 재생; 만료·결측·중복 시험 | 미래 정보 없음, 예측 표시 일치, 조치 불가 사유 추적 | 별도 구현 필요 |
| C. 그림자 운영 | 실제 관측으로 예보하되 기존 현장 판단과 비교 | 도착 지연·실패·경보 부담·조건별 성능을 충분한 표본으로 측정 | 현장 연동 미확인 |
| D. 운영자 승인 실증 | 정해진 작업·기간에서 후보 권고와 결과 수집 | 준비시간·납기·품질·반동 피크를 포함한 사전 기준 충족 | 제안 |
| E. 동기화·검증된 운영 모델 | 실측 상태·조치 반응으로 모델 보정, 후보 평가 검증 | 실측 대비 상태·반응 오차와 목적별 유효성을 증명 | 장기 검토 |

기간·공장·피크 사건 수·허용 오경보·위반률의 수치 기준은 현장 비용과 표본 설계를 보고 실증 전에 정해야 한다. 이 문서는 근거 없는 “정확도 95%”나 성숙도 점수를 부여하지 않는다. 대회 holdout 승인은 연구 평가의 별도 문이며 현장 배포 승인과 동일하지 않다.

### 8.1 도메인별 평가 지표

| 평가 대상 | 권장 지표 | 해석 주의 |
|---|---|---|
| 예측 | 피크 MAE, 에피소드 F1, FP, 거리별 기준선 차이·CI | 주·보조 지표와 사전 선정 순서 보존 |
| 불확실성 | 명목 대비 커버리지, pinball, 폴드·조건별 표본 수 | pooled 결과로 취약 조건을 감추지 않음 |
| 경보 | 가동시간당 오경보, 사건별 탐지, 원점 기준 선행시간, 확인 소요 | 위치 FP와 운영 사건을 구분 |
| 조치 | 제안·승인·거절·만료·실행·완료 수와 각 분모, 제약 위반 | 승인율과 실제 완료율을 구분 |
| 운영 결과 | 실현 피크, 생산량·납기·품질, 반동 피크, 추가 작업 부담 | 단순 전후 차이를 인과 절감으로 단정하지 않음 |
| 시스템 | 데이터 신선도, 모델/화면 지연, 누락/중복, 복구 시간 | 개발 CV 31분21초로 온라인 성능을 추정하지 않음 |

### 8.2 시뮬레이터와 디지털 트윈

현재 부하 이동 계산은 **가정 기반 시나리오 분석**으로 설명하는 것이 적절하다. 운영 디지털 트윈을 목표로 한다면 계측 범위·설비 상태·생산 제약·조치 반응을 모델에 연결하고, 실제 관측과 동기화·보정하며, 목적에 맞는 오차와 불확실성을 평가해야 한다. 3D 화면 추가 자체가 트윈의 근거는 아니다.

참고서 10·14장의 원리를 전력 도메인에 옮긴 판단이며, 제조 트윈의 구조적 검토에는 [NIST의 ISO 23247 적용 사례](https://www.nist.gov/publications/use-case-scenarios-digital-twin-implementation-based-iso-23247)를 보조 자료로 쓸 수 있다. 이번 서비스에 ISO 적합성을 평가한 것은 아니다.

## 10. 이번 검토의 확인 범위

검증 명령과 직접 종료코드는 [validation.json](../../../outputs/reviews/2026-09-28/validation.json)에 저장했다. **기존 테스트 141개가 29.29초에 통과했고 직접 종료코드는 0**이다. `run_all.py --dry-run-freeze`도 직접 종료코드 0, `ready_for_human_approval`, `holdout_read=false`를 반환했다. 개발 캐시 유효성, 과학 코드 지문·원자료 및 동결 증거의 해시 불변과 실제 예약 `Disabled`를 확인했다. 전체 재학습, 새로운 성능 실험, 최종 테스트 평가, 원자료를 전부 읽는 prototype 테스트는 이번 범위에 포함하지 않았다.

시각화는 390/800/1024/1440px에서 렌더링하여 페이지 가로 넘침, 텍스트 대비, 조작 영역, 링크·필터·접기/펼치기, 좁은 화면의 표 내부 스크롤을 확인했다. 독립 화면 검토에서 발견한 모바일 라벨·표의 압축, 흐름도 연결, 예측거리 명칭, 우선순위 연결을 수정했다. 상세 결과는 같은 출력 폴더의 [visual_validation.json](../../../outputs/reviews/2026-09-28/visual_validation.json) 및 화면 이미지에 남겼다. 이는 문서·화면 QA이며 현장 효용의 검증이 아니다.

자료 재생성·확인 명령은 저장소 루트 기준 다음과 같다. 시각화 생성은 기존 개발 표를 읽으며 모델을 학습하지 않는다. `qa_visual.py`는 선택 의존성 Playwright/Chromium을 사용한다.

```powershell
.\.venv\Scripts\python.exe -X utf8 docs/reviews/2026-09-28/build_visual.py
.\.venv\Scripts\python.exe -X utf8 docs/reviews/2026-09-28/qa_visual.py
.\.venv\Scripts\python.exe -X utf8 docs/reviews/2026-09-28/audit_review.py
```

최종 수치의 근거 우선순위는 **최신 선정/비교 표 → 최신 P3 인계·재현 기록 → 이전 보고서 → 시연 화면**이다. 과거 보고서에서 최신 선정으로 연결되지 않는 결과는 이전 체크포인트로 표기한다. 이번 정리는 공식 단위 답변, 최종 holdout 성능, 실제 공장 제약이나 현장 절감 성과를 새로 확보하지 않았다.
